# 全局工作规则

## 适用范围与语言

- 本文件保存跨项目通用的个人工作偏好，包括代码通用标注和仓库组织原则；具体目录树、环境和语言风格由项目规则约定。
- 回复、注释、提交信息及建议使用中文；代码标识符、命令、路径、配置键和必要的技术术语保留原写法。
- 遵循当前用户明确要求；用户针对本次任务作出的例外优先于这里的默认偏好，并遵守运行环境的更高优先级约束。

## 阅读与任务组织

- 修改已有文件前必须先读取，理解上下文后再操作；不得对未读过的代码直接提出具体修改建议。
- 多文件、跨模块或存在依赖的任务，先梳理目标、约束和执行顺序，再逐步实施与验证；单文件小改采用简短流程，纯问答直接回答。

## 修改范围与设计

- 只实施用户要求及完成目标必需的修改，不额外添加功能、配置、重构或优化。
- 不顺手修改周边代码、补充无关注释或批量调整格式；保留用户已有修改。
- 避免过早抽象，少量相似代码可以保留；不引入仅为未来可能需求准备的抽象层或兼容性代码。
- 系统边界校验外部输入；内部函数在契约明确时信任调用方，不为不可能发生的场景添加防御和回退逻辑。

## 仓库目录规范

- 新建文件按功能和用途放入对应目录，不随意堆放在根目录；根级规则、依赖清单和工具要求的配置文件除外。
- 源代码、编译产物、测试和文档分类存放，编译产物目录不存放源码。
- 目录名称应明确表达用途，避免 other、misc 等含糊名称。
- 修改已有仓库时遵循现有结构，不擅自重组目录或调整工具自动生成的结构。
- 具体目录树和路径以项目规则为准，不要求所有项目采用同一种技术栈的工程目录。

## 代码通用标注

- 以下要求适用于自有源码；第三方代码和自动生成文件不强制套用。项目存在明确的版本或标注约定时，以项目规则为准。
- 自有代码文件头记录文件名或功能、描述、版本、日期及修改记录；新文件从 `v1.0` 开始，已有文件沿用实际版本，不编造作者和历史。
- 日期统一为 `YYYY/MM/DD`，版本用 `vX.Y`；修改记录最新在前，仅保留最近 3 个版本，头部版本与最新记录一致。
- 在新增或修改的逻辑块上方标注版本、日期、动作和说明；连续属于同一变更的代码可用一个标注，不要求逐行重复。
- 标注版本与文件头一致；接口变更在函数头或提交正文中说明受影响的调用方。

```text
// vX.Y YYYY/MM/DD 新增：说明新增逻辑
// vX.Y YYYY/MM/DD 修改：说明变更内容和原因
// [废弃] vX.Y YYYY/MM/DD 废弃原因，替代方案，计划在 vX.Z 清理
```

- C/C++ 和 Verilog 使用 `//`，Python 使用 `#`，MATLAB 使用 `%`；其他语言使用其合法的注释语法。
- 将废弃代码注释保留，注明原因、替代实现和计划清理版本，经过 3 个版本后清理；执行清理时遵守操作授权规则。
- 各语言的文件头样式由项目规则补充；普通文档不套用源码标注格式。

## 需要明确授权的操作

- 删除文件、目录或 Git 分支，以及 `git reset --hard`、强制推送、`git rebase`，执行前说明对象和影响并确认授权。
- 清空数据库表、覆盖未备份数据、修改 CI/CD 流水线或共享基础设施，同样需要明确授权。
- 用户已在当前任务中明确授权具体操作及范围时，不重复询问；不要把普通编辑文件理解为整文件破坏性覆盖。

## 错误处理与安全

- 不静默吞掉错误：捕获后记录适当日志或向上传递，不使用空的 catch 或错误分支掩盖失败。
- 只处理真实可能发生的错误；验证用户输入、外部 API、网络或串口报文、文件内容等系统边界数据。
- 禁止将外部输入直接拼入 shell 命令。
- 不在源码中硬编码密钥、密码、Token 或证书私钥；通过环境变量或不纳入版本管理的独立配置提供。
- 不提交 `.env`、`credentials.json`、`secrets.*` 等敏感文件，并为项目中的敏感文件设置适当忽略规则。
- 日志和调试输出不得泄露凭据或隐私数据；正式版本的敏感调试输出应关闭或脱敏。
- 不引入来源不明、缺乏维护的第三方库；在项目依赖文件中记录版本，便于复现和排查问题。

## Git 提交习惯

- 默认在每次实质性修改完成并完成必要验证后执行一次本地 `git commit`。用户明确要求不提交时遵循用户要求；非 Git 工作区或没有变更时不提交。
- 提交前检查工作区、暂存区和差异，只提交本任务产生的改动；不得夹带用户已有改动，也不得为便于提交而撤销它们。
- 若无法可靠分离改动、缺少 Git 身份或验证失败，说明具体阻碍，不强行提交，不擅自修改全局 Git 配置。
- 本地提交不包含自动推送、发布或修改远端历史的授权。
- 提交信息使用 `<类型>(<范围>): <简短中文描述>`，范围填写实际模块或子系统。
- 类型使用 `feat`、`fix`、`refactor`、`docs`、`style`、`test`、`chore`。
- 简短描述使用中文祈使句，最多 50 个字符，例如“新增超时重传逻辑”，避免“新增了……”等完成时表达。
- 接口变更在提交正文中说明影响范围；不添加 AI 署名或 AI 的 Co-Authored-By 行。

## 验证与反馈

- 根据实际修改运行项目已有的相关检查；不要凭空编造构建或测试命令。
- 明确区分已完成、已验证和未验证的内容；失败时说明原因，不声称成功。
- 完成后简要给出结果、验证情况和必要的提交信息；不在回复末尾再次重复相同总结。
