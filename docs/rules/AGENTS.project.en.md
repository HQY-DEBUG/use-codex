## Scope

- All paths in this file are relative to the target project root.
- Apply rules only to the directories and languages involved. Do not create unnecessary modules just to match the directory tree.
- Preserve tool-generated structures, third-party interfaces, and existing public identifiers. Apply the relevant conventions when creating or modifying first-party code; do not rewrite unrelated files in bulk.
- This file consolidates the original scattered rules and does not depend on the original `ref/` directory or Copilot's `applyTo` field.
- Follow the installed global rules for general working habits, repository organization, and code annotations. This file adds project-specific conventions. Install one global version and one project version together.

- `<project-name>/` is a placeholder for the FPGA project directory; replace it with the actual project name.

- Do not manually change the top-level structure generated by Vitis IDE.

## Python Runtime Environment

- Use the system-wide Python interpreter for this project's first-party Python code. Do not create or activate environments with venv, virtualenv, conda env, pipenv, or similar tools.
- Confirm the actual interpreter before execution. Run scripts with `python script.py` and install packages with that same interpreter using `python -m pip install <package>`.
- When needed, keep dependencies in the root `requirements.txt` and install them into that system interpreter with `python -m pip install -r requirements.txt`.
- This preference applies only to this project, not to other projects or external tools' runtimes.

## Naming

| Object | Rule |
| --- | --- |
| C/C++ variables and ordinary functions | snake_case, such as `recv_buf` and `init_dma()` |
| C/C++ macros, globals, and members | UPPER_SNAKE_CASE for macros; `g_` for globals; snake_case with optional `m_` for members |
| C/C++ classes and structs | PascalCase for new names, such as `UdpWorker`; preserve existing snake_case struct names |
| Python variables, functions, classes, and constants | snake_case variables/functions, PascalCase classes, UPPER_SNAKE_CASE constants, single leading underscore for private members |
| MATLAB variables, functions, and constants | snake_case variables/functions; UPPER_SNAKE_CASE constants |
| Verilog modules and signals | snake_case; UPPER_SNAKE_CASE parameters and macros |
| Verilog delayed and reset signals | `_r` for delayed signals, `_r1` and `_r2` for multiple stages; `rstn` active-low and `rst` active-high reset |
| Verilog input/output disambiguation | Add `_i` to inputs and `_o` to outputs only when needed; do not add these suffixes to AXI/AXIS or similar bus interface signals |
| Qt signals, slots, and UI members | Signals such as `dataReceived`, slots such as `onDataReceived`, and UI members such as `m_btnSend`; these override ordinary C++ naming |

- Names should express purpose. Avoid single-letter names except loop variables such as `i`, `j`, and `k`.
- Prefix C/C++, Python, and Qt Boolean variables with `is_`, `has_`, or `can_`. Do not apply this requirement to Verilog.

## C/C++: .c, .h, .cpp, .hpp

- Indent with 4 spaces, not tabs. Use K&R braces, with opening braces on the same line.
- Keep function calls and their arguments on one line; do not split arguments across lines.
- Write ordinary comments in Chinese using `//`. Use `// ---- 内容 ----//` for section labels.
- Allow `/* ... */` in file headers and `/** ... */` in Doxygen function headers. Do not use block comments for other inline or standalone comments.
- Vertically align trailing comments in contiguous groups of struct fields, macros, and initialization entries.
- Use Chinese Doxygen function headers describing actual parameters, return values, and relevant notes:

```cpp
/**
 * @brief  函数用途
 * @param  param1 参数说明
 * @return 返回值说明
 * @note   注意事项或接口影响（按需填写）
 */
```

- First-party status-returning interfaces use `0` for success and negative values for errors. Follow the actual contracts of third-party APIs and functions returning pointers or data values.
- Check results of calls that may fail, including malloc, fopen, and hardware access with status returns. Report errors through the logging module, not directly with printf.
- Use the following file header for `.c` and `.h` files; preserve equivalent version fields in other first-party source files:

```c
/*
 * 文件 : xxx.c
 * 描述 : 模块说明
 * 版本 : v1.0
 * 日期 : YYYY/MM/DD
 *
 * 修改记录（最新在前，最多 3 条）:
 * 版本  作者  日期        修改内容
 * v1.0  ---   YYYY/MM/DD 创建文件
 */
```

## Qt C++: Code Under PC/qt/

- Apply these rules in addition to the C/C++ rules. They also apply to existing projects using `qt/`; do not relocate an entire project just to standardize the path.
- QWidget / QMainWindow in the GUI thread handle UI updates without lengthy network or IO work. Put expensive work in a worker thread, retaining the existing QThread subclass or worker-object structure.
- Send cross-thread messages through Qt signals and slots using `Qt::QueuedConnection`. Never access widgets directly from worker threads.
- Put `Q_OBJECT` at the beginning of custom QObject-derived class declarations. QObject / QThread worker constructors accept `QObject *parent = nullptr` and pass it to the base class; QWidget-derived controls use `QWidget *parent = nullptr`.
- Prefer Qt parent-child ownership for object lifetimes. Create and destroy cross-thread objects according to their thread affinity.
- Stop threads cooperatively: call `quit()` for event-loop threads and release resources after completion. Custom run loops must check a stop flag or interruption request and unblock pending operations; quit alone is insufficient. Never call `terminate()` directly.
- Do not assume slots on a QThread subclass execute in the worker thread. Use a worker object with the correct thread affinity when slots must execute there.

## Python: First-Party .py Files

- Use a module docstring to record the filename, purpose, version, date, and change history. Function docstrings describe purpose, Args, and Returns; class docstrings describe purpose and Attributes.
- Write inline comments in Chinese with `#`. Follow the global rules for change annotations.
- Catch specific exceptions. Do not use bare `except:` or broad `except Exception:` except as a top-level fallback. Use `with` for resources supporting context management, ensuring files and sockets are released.
- PyQt5 GUI threads only update the UI. Worker threads manage their own sockets and other resources; communicate across threads only through signals and slots, without accessing widgets directly.
- In high-throughput scenarios, use deque for batch queue operations, timers to flush logs in batches, and rate-limited setText calls for status labels.

```python
"""
文件名.py -- 模块说明
版本 : v1.0
日期 : YYYY/MM/DD

修改记录（最新在前，最多 3 条）:
    v1.0 YYYY/MM/DD 创建文件
"""
```

## Verilog / SystemVerilog: .v, .sv, .vh, .svh

- Indent with 2 spaces, not tabs. Put begin on its own line, not on the same line as always, if, else, for, or similar constructs.
- Use explicit `1'b0` and `1'b1` in single-bit comparisons and assignments, not unsized `0` and `1`.
- Use nonblocking assignments `<=` for sequential logic and blocking assignments `=` for combinational logic.
- Declare one port per line, aligning direction, type, width, name, and comma in columns, with a trailing Chinese `//` comment.
- Align register and signal declarations by type, width, name, and semicolon, with a trailing Chinese `//` comment.
- Include default in combinational case statements. Assign every combinational output on every path, using initial defaults where needed; adding default alone must not leave latches inferred.
- Check metastability risks when releasing asynchronous reset and synchronize according to the clock domain's requirements.
- File headers use Function, Version, Date, Description, and Modify fields. Follow the global version-history rules:

```verilog
/**************************************************************************/
// Function   : 模块功能
// Version    : v1.0
// Date       : YYYY/MM/DD
// Description: 详细说明
// Modify:
// version     date        modify
// v1.0        YYYY/MM/DD  创建文件
/**************************************************************************/
```

## MATLAB: .m Files

- Use `%` file-header comments to record the file, description, version, date, and change history.
- Immediately follow function declarations with `%` help comments describing purpose, inputs, and outputs. Use Chinese `%` comments and `%% 内容` for section headings.
- Prefer matrix operations over loops; briefly explain why a loop is needed when using one.
- Avoid indiscriminate clear all / close all. Perform explicit cleanup at the start of a script only when necessary.
- Give plots titles, axis labels, and units. Follow global rules for code change annotations.

## Project Documents: First-Party Markdown Under doc/

- Begin the document body with a level-one title, followed by a quoted version/date block, a change-history table, and a separator.
- List history newest first and retain only the latest 3 versions. Increment the minor version for normal changes and the major version for substantial restructuring.
- Match the header version to the newest history entry and use `YYYY/MM/DD` dates. Write change descriptions as Chinese imperatives such as “新增……”.
- Apply this format to authored project documents. Do not insert version headers into external references, official snapshots, or generated files in bulk. AGENTS.md itself only needs a clear rules structure.

```markdown
# 文档标题

> 版本：v1.0　日期：YYYY/MM/DD

## 修改记录

| 版本 | 日期 | 修改内容 |
| --- | --- | --- |
| v1.0 | YYYY/MM/DD | 创建文档 |

---

正文内容
```
