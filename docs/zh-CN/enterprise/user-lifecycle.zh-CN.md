<a id="user-lifecycle-management"></a>

# 用户生命周期

> 有关完整的文档索引，请参阅 [llms.txt](https://learn.chatgpt.com/llms.txt)。通过将 `.md` 附加到页面 URL 即可获得文档页面的 Markdown 版本。

使用本指南可在员工加入时为其提供正确的 ChatGPT 工作区访问权限，在其职责发生变化时更新该访问权限，并在其离开时删除访问权限。该流程还涵盖工作区席位、基于组的角色、Codex 访问令牌以及具有自己的访问控制的连接系统。

单点登录 (SSO) 可验证员工的身份。配置将员工添加到工作区。这两种操作都不能单独决定员工的席位、功能权限、本地运行时策略或对外部系统的访问权限。

跨三个生命周期里程碑管理员工访问：

- **加入：** 配置工作区访问权限、组、角色和正确的座位。
- **移动：** 更新员工组并仅删除过时的直接角色。
- **离开：** 删除工作区访问权限、撤销令牌并审查连接的系统。

<a id="verify-prerequisites-and-assign-owners"></a>

## 验证先决条件并分配所有者

在员工入职之前，确定谁控制生命周期的每个部分：

| 所有者 | 责任 |
| ------------------------- | ----------------------------------------------------------------------------------------------------- |
| 工作区所有者 | 启用目录同步、分配工作区角色、批准席位类型以及审查审核访问权限 |
| 身份管理员 | 配置身份提供程序、应用程序分配、配置组和同步状态 |
| 工作区管理员 | 查看工作区成员、组成员资格和支持的管理设置 |
| 安全或服务所有者 | 审查 Codex Token、连接系统、共享自动化和所需的审计证据 |

确认目标工作区，在需要时验证组织的电子邮件域，并确定可以启用目录同步的工作区所有者。然后检查工作区计划支持哪些控件：

| 功能 | 支持的工作区计划 |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------ |
| 通过 SCIM 进行目录同步 | ChatGPT 企业、教育和医疗保健 |
| 自定义角色和基于角色的访问控制 | ChatGPT 企业、教育、医疗保健和教师 |
| Codex 访问令牌 | ChatGPT 商业和企业 |
| 仅 Codex 席位 | 合格企业和合格的现有业务工作区；教育机构、教师或医疗保健机构无法使用 |

SCIM 代表跨域身份管理系统。业务工作区可以在没有 SCIM 的情况下支持 Codex 访问令牌，而教育工作区可以在没有 Codex 访问令牌或仅限 Codex 的席位的情况下支持 SCIM。仅应用您的工作区可用的控件。

仅当业务工作区在 2026 年 6 月 24 日之前拥有 Codex 席位，或者截至该日期有合格的待处理 Codex 席位邀请时，才可以保留和添加仅限 Codex 的席位。新的商务工作区和没有合格席位或邀请的工作区无法添加第一个仅限 Codex 的席位。参见 [管理 ChatGPT Business 中的工作区生命周期和迁移](https://help.openai.com/en/articles/8801890-managing-workspace-lifecycle-and-migration-in-chatgpt-business)。

如果工作区支持多种席位类型，请在启用自动配置之前查看 **工作区设置 > 身份和访问** 中的默认设置。 SCIM 配置的用户继承该默认设置，并且席位控制哪些产品使用界面可用。自定义角色无法授予席位不包含的访问权限。

使用 **权限和角色** 检查本地访问、访问令牌、凭证生命周期和远程设备控制。某些工作区将 **Codex 和工作本地** 中的本地访问与 **允许成员使用 Codex 并在本地工作** 控件相结合。其他人将 **Codex 本地**（带有 **允许会员本地使用Codex**）与 **本地工作**（带有 **在本地使用工作**）分开。单独的 Codex 和工作控件不会授予彼此访问权限。令牌控件出现在本地访问部分或单独的 **访问令牌** 部分中。这些设置独立于组成员身份和分配的座位类型。

<a id="choose-how-employees-join-the-workspace"></a>

## 选择员工加入工作区的方式

为每个受众选择一种主要配置方法：

| 方法 | 访问如何开始 | 从何处删除访问 |
| -------------------------- | ----------------------------------------------------------------------- | ------------------------------------------------------- |
| 手动邀请 | 工作区所有者或管理员邀请员工 | 工作区成员管理 |
| 自动帐户创建 | 具有合格电子邮件域的员工登录 | 工作区管理和相关身份流程 |
| 与 SCIM 的目录同步 | 身份管理员在身份提供程序 | 中分配员工 身份提供程序应用程序或配置组 |

对小型试点或不通过目录同步管理的组使用手动邀请。当工作区成员身份应在员工加入、更换团队或离开时遵循身份提供者时，请使用 SCIM。

不要同时启用自动帐户创建和 SCIM。通过自动帐户创建添加的用户可能缺乏 SCIM 管理，因此从身份提供者组中删除他们可能不会删除他们的工作区访问权限。请参阅 [SCIM 集成常见问题解答](https://help.openai.com/en/articles/10011769-openai-platform-scim-integration-faq) 了解当前指南。

SCIM 可以连接单个 ChatGPT 工作区或组织的租户，具体取决于批准的身份设置。保持每个工作区和产品分配明确。共享目录连接不会自动授予或删除每个工作区或平台 API 组织的访问权限。

<a id="connect-a-provisioning-group-to-the-correct-workspace"></a>

## 将配置组连接到正确的工作区

在添加第一个试点员工之前配置连接。工作区所有者和身份管理员具有不同的职责：

1. 让工作区所有者选择预期的 ChatGPT 工作区并检查 **工作区设置 > 组**。记录现有组名称、成员、自定义角色分配以及相关项目或 GPT 共享。
2. 让身份管理员确定要同步的确切身份提供者组。将其名称和成员资格与每个现有工作区组进行比较。
3. 如果已同步的组与现有工作区组共享名称，请在启用同步之前协调或重命名冲突的组。让工作区所有者批准生成的成员、继承的角色和共享。匹配的现有组将由 SCIM 管理，并且其成员资格将切换到身份提供者控制。
4. 选择一个范围狭窄的试点小组，并记录批准的工作区、预期员工和小组角色分配。
5. 让工作区所有者打开 **工作区设置 > 身份和访问** 并选择 **启用目录同步**。如果出现提示，请选择 **仅将 SCIM 用于此工作区** 进行工作区级别配置，或选择 **保留跨产品扩展的选项** 进行批准的租户级别配置。如果租户级 SCIM 已处于活动状态，请管理现有连接，而不是创建第二个工作区连接。
6. 让身份管理员完成身份提供商连接，选择 ChatGPT 应用程序，然后分配批准的组以将成员配置到预期工作区中。
7. 在 **工作区设置 > 组** 中，确认所选组显示其 SCIM 徽章。在使用组名称、同步成员和目标工作区进行访问之前，请验证组名称、同步成员和目标工作区。
8. 让工作区所有者打开 **权限和角色 > 自定义角色**，创建或选择批准的角色，并将其分配给同步组。角色配置可在 Web 上进行，并且需要工作区所有者访问权限。
9. 在添加代表试点员工之前，请检查组的有效权限和默认工作区座位类型。

身份提供者管理员控制应用程序和组成员身份；工作区所有者控制目录同步和工作区角色分配。有关当前提供商特定的步骤和可用性，请参阅 [SCIM 集成常见问题解答](https://help.openai.com/en/articles/10011769-openai-platform-scim-integration-faq) 和 [配置基于角色的访问控制](https://help.openai.com/en/articles/11750701-rbac)。

<a id="provision-a-new-employee"></a>

## 配备一名新员工

对于通过 SCIM 管理的员工：

1. 确认预期的工作区、经过验证的电子邮件地址、默认席位类型和身份提供商组。
2. 将员工分配到身份提供程序中的 ChatGPT 应用程序或访问授予组。
3. 允许目录同步完成。如果员工没有出现，请检查当前身份提供者状态。
4. 在 **工作区设置 > 成员** 中，验证员工的电子邮件、会员资格或待处理的邀请、席位类型和 SCIM 徽章。
5. 在**工作区设置 > 组**中，确认员工属于预期同步组。让工作区所有者验证分配给该组的自定义角色。
6. 让一名代表员工登录到正确的工作区，并验证他们所需的特定产品使用界面、功能和连接系统。
7. 使用组织批准的流程记录访问所有者和成功验证。

如果您手动添加员工，请从工作区成员管理发送邀请，然后执行相同的席位、组、角色和登录检查。

群组可以组织成员，但不会单独授予对每个功能的访问权限。有关当前角色分配过程，请参阅 [角色和工作区权限](roles-and-workspace-permissions.zh-CN.md) 和 [配置基于角色的访问控制](https://help.openai.com/en/articles/11750701-rbac)。

<a id="update-access-when-an-employee-changes-teams"></a>

## 当员工更换团队时更新访问权限

更换团队的员工可以保留以前的组或角色分配的访问权限。在验证新的访问级别之前更新拥有成员资格的源：

1. 确定员工的新团队、所需的工作区、席位、批准的功能权限和目标组。
2. 如果员工在整个变更过程中必须留在工作区，请先将员工添加到批准的目标组，然后再将其从之前的组中删除。更新身份提供商中 SCIM 管理的成员资格；通过工作区管理更新手动管理的成员资格。
3. 确认已批准的角色已分配给目标组。保留共享组上的现有角色分配，以便其他成员保留其批准的访问权限。
4. 仅在批准单独的组范围策略更改并检查其对每个成员的影响后，工作区所有者才能更改组到角色的分配。
5. 让工作区所有者打开员工的个人资料，查看 **直接角色**，然后删除直接分配给该人员的过时角色。自定义角色使用 **默认**、**开** 和 **关闭**。任何分配的角色中的显式 **关闭** 都会覆盖另一个角色中的 **开**。
6. 在批准团队变更之前，请检查员工在所有直接角色和组分配角色中的有效权限。
7. 如果工作区支持多种座位类型，请让工作区所有者打开 **工作区设置 > 成员 > 更改座位类型** 并检查员工的预期产品访问权限。
8. 在将 ChatGPT 席位转换为仅 Codex 席位之前，请确认员工应失去对聊天、内存、项目和其他 ChatGPT 功能的访问权限。如果员工返回 ChatGPT 座位，基础数据不会被删除并再次可用。
9. 同步和权限更新完成后，验证新允许的操作和不应再可用的操作。

如果员工拥有自动化工作流程，请检查其 Codex 令牌、机密管理器条目或连接服务授权是否应移至其他批准的所有者。删除员工的本地 Codex 权限会暂停该员工的 Codex 令牌，但不会撤销它们。恢复权限会重新激活这些令牌，因此请撤销必须永久失去访问权限的凭据。

<a id="remove-a-departing-employee"></a>

## 删除离职员工

从拥有员工工作区成员资格的系统开始：

1. 确定 SCIM 管理员工还是管理员手动添加员工。
2. 对于 SCIM 管理的员工，删除该员工的 ChatGPT 应用程序分配，并从身份提供程序中的每个授予访问权限的配置组中删除该员工。不要删除共享组本身。
3. 对于不通过 SCIM 管理的员工，请让工作区所有者或管理员从 **工作区设置 > 成员** 中删除该成员。
4. 确认该成员不再出现在预期工作区中。对于 SCIM 管理的访问，请验证同步是否已完成，并且没有其他身份提供者分配可以恢复成员身份。
5. 记录已完成的删除并指定所有者来审查令牌、连接的系统和保留的数据。

当身份提供商仍将员工分配到 SCIM 管理的组时，请勿依赖工作区端删除。稍后同步可以将员工添加回工作区。

<a id="revoke-codex-access-tokens-and-transfer-automation"></a>

### 撤销 Codex 访问令牌和传输自动化

从工作区中删除人员并不能取代对可信自动化所使用的凭据的明确审查。仅当工作区支持并启用 Codex 访问令牌时才应用此过程。

删除本地 Codex 权限会暂停现有令牌，但不会撤销它们。如果工作区所有者恢复权限，这些令牌可以再次使用，因此请显式撤销必须永久失去访问权限的凭据。

**访问令牌** 页面标识每个Token的创建者和状态。使用 **撤销** 删除活动令牌的访问权限：



> 插图：ChatGPT 访问令牌显示令牌名称、其创建者和状态以及撤销操作。



1. 让工作区所有者或管理员打开 [访问令牌](https://chatgpt.com/admin/access-tokens)。
2. 识别离职员工创建的令牌以及使用这些令牌的工作流程。
3. 选择替换身份。对于符合条件的即用即付计划的持久非人工工作流程，请使用经批准的专用 [服务帐户](service-accounts.zh-CN.md)。否则，请确定已批准的活动工作流程所有者。如果需要，请工作区所有者授予该人员访问令牌创建权限，并确认该人员具有本地 Codex 权限。
4. 创建替换令牌。获得许可的服务帐户操作员可以从服务帐户的详细信息页面创建令牌。对于个人替换，请让新的工作流程所有者为其自己的 ChatGPT 工作区身份创建令牌。如果对话框显示 **范围**，请选择 **Codex**。仅当工作流程需要时才选择其他范围。没有 **范围** 的对话框会创建仅 Codex 的令牌。管理员无法代表其他用户创建个人令牌。
5. 更新工作流的存储机密，然后使用替换令牌验证它是否成功运行。
6. 让工作区所有者或管理员撤销离职员工的令牌和任何替换的凭据。
7. 确认已撤销的令牌无法再启动新的经过身份验证的运行。

当批准的替换所有者创建令牌时，请使用描述性工作流程名称并选择组织策略允许的最短凭证生命周期。如果出现 **范围**，请选择 **Codex** 并避免工作流不需要的权限。以下示例显示了作用域接口：



> 插图：ChatGPT 创建访问令牌对话框，显示名称、选择 Codex 的范围、到期时间和创建操作。



工作区所有者和管理员可以撤销其工作区中的任何令牌。具有访问令牌权限的成员只能撤销他们创建的令牌。有关当前令牌权限和轮换步骤，请参阅 [访问令牌](access-tokens.zh-CN.md#rotate-or-revoke-a-token)。

<a id="review-connected-systems-and-retained-data"></a>

### 审查连接的系统和保留的数据

工作区配置并不管理每个授权边界。要求相关服务所有者审查对以下内容的访问权限：

- 源仓库和连接的 GitHub 帐户。
- Google Drive、Slack 和其他连接的应用程序。
- 安装的插件、捆绑的技能和连接器支持的功能。
- 托管 Codex 环境、共享自动化和存储的机密。
- 托管设备、本地存储的凭据以及支持的远程会话。
- 单独的平台 API 组织、项目和 API 密钥。

应用每个系统拥有的控件，而不是假设工作区组或 SCIM 更改会更新各处的权限。请参阅 [角色和工作区权限](roles-and-workspace-permissions.zh-CN.md) 了解完整的边界模型，请参阅 [插件控件](apps-and-connectors.zh-CN.md) 了解插件可用性、捆绑技能和连接应用程序权限。

删除工作区访问权限与删除内容不同。当成员离开时，工作区会自动将其项目和自定义 GPT 所有权重新分配给工作区所有者。这些项目不会被标记为删除。如果该成员重新加入，所有权将返回该成员。

对于 Enterprise 和 Edu 工作区、聊天、文件和画布文档遵循配置的工作区保留策略。业务工作区无限期地保留聊天、文件和画布文档。医疗保健工作区还提供数据保留控制；查看适用的工作区配置和 [ChatGPT 医疗保健指导](https://help.openai.com/en/articles/20001046-chatgpt-for-healthcare)。

重新分配项目或 GPT 不会转移前成员的私人对话或文件，并且工作区所有者无法通过所有权更改查看该私人内容。有关当前计划特定的行为，请参阅 [工作区成员删除和数据保留](https://help.openai.com/en/articles/8266418)。

如果安全性或合规性需要更改证据，请在批准的系统中记录受影响的工作区、员工、身份提供者分配、完成时间、批准所有者和令牌撤销验证。确认经过身份验证的 [管理 API 参考](https://chatgpt.com/admin/api-reference) 中的可用记录、管理员权限和保留情况。敏感的合规范围可能需要工作区所有者。有关产品概述，请参见 [合规性 API 和审核事件](compliance-api.zh-CN.md)。请勿从本指南推断事件覆盖范围、字段或保留期限。

<a id="troubleshoot-missing-or-unexpected-access"></a>

## 解决丢失或意外访问的问题

| 症状 | 检查内容 | 纠正措施 |
| ----------------------------------------------------- | ----------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| 员工可以登录，但找不到工作区 | 目标工作区、邀请、身份提供者分配和电子邮件地址 | 更正分配或电子邮件映射，然后验证工作区成员资格 |
| 同步员工收到错误座位 | 工作区的默认座位类型和当前成员记录 | 让工作区所有者检查默认座位选项和员工支持的座位选项 |
| 团队更改不会删除功能 | 其他组成员身份、**直接角色** 和员工的组合权限 | 从过时的组中删除员工，然后让工作区所有者仅撤销该员工的过时直接角色 |
| 手动组未经批准即由 SCIM 管理 | 匹配组名称、身份提供者成员、继承的角色和现有共享 | 协调身份提供者中已批准的组成员身份并审查受影响的访问 |
| 团队更改后其他员工失去访问权限 | 最近对共享组角色分配的更改以及前团队批准的访问权限 | 让工作区所有者恢复批准的共享组角色，然后仅更新移动员工的成员身份 |
| 团队变更后自动化令牌停止工作 | 工作流所有者的本地 Codex 权限和当前令牌状态 | 让工作区所有者恢复批准的本地 Codex 访问，或轮换和撤销受影响的令牌 |
| 访问更改不会立即出现 | 身份提供商同步状态、预期同步窗口和最近的角色更新 | 让身份管理员在联系 OpenAI 支持之前验证同步 |
| 已删除的员工返回工作区 | 身份提供程序应用程序分配和每个授予访问权限的配置组 | 在身份提供程序中删除员工，而不是仅在工作区设置中 |
| 离职员工仍然拥有列出的令牌 | 令牌创建者、工作流所有者和工作区管理员的令牌权限 | 轮换任何所需的自动化凭证，然后撤销离职员工的令牌 |
| 连接的应用程序仍允许访问 | 源系统的帐户、插件可用性和应用程序授权 | 要求相关服务所有者使用该系统支持的控件删除访问权限 |

大多数身份提供商每 30 到 40 分钟同步一次，但有些身份提供商会立即应用更新。自定义角色更改可能需要大约五分钟才会出现。您无法强制 SCIM 同步，因此请勿删除并重新创建工作区成员来解决延迟更新问题。

如果在预期的特定于提供商的窗口之后访问删除或组更新仍未完成，请让身份管理员收集：

- 受影响的工作区和员工电子邮件地址。
- 身份提供者、应用程序分配和配置组。
- 尝试的更改、其时间戳和最新同步状态。
- 仍需要审核的直接角色、组角色或令牌。

通过帮助中心联系 [OpenAI 支持](https://help.openai.com/) 并提供这些详细信息。将保留访问权限的离职员工视为安全例外，并遵循组织的事件升级流程。

对于特定于提供商的设置和同步行为，请使用当前的 [SCIM 集成常见问题解答](https://help.openai.com/en/articles/10011769-openai-platform-scim-integration-faq)。有关登录和身份错误，请参阅 [身份验证故障排除](https://help.openai.com/en/articles/10489721-login-and-authentication-faq-s-and-troubleshooting-sso-scim-and-domain-verification)。

<a id="verify-the-complete-employee-lifecycle"></a>

## 验证完整的员工生命周期

在更广泛的部署之前，使用代表性测试员工来验证所有三个转换：

| 生命周期阶段 | 主要所有者 | 成功结果 |
| --------------- | ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| 加入者 | 身份管理员 | 员工加入具有预期座位、组和功能访问权限的正确工作区 |
| 移动者 | 身份和工作区所有者 | 管理员更新组成员身份，工作区所有者删除过时的直接角色，同时保留共享组角色 |
| 离开者 | 身份和安全所有者 | 管理员删除工作区访问权限、查看支持的令牌以及撤销或重新分配外部访问权限 |

记录每个更改的批准者、您验证的内容以及负责解决任何剩余访问异常的所有者。根据您组织的身份和安全策略安排定期访问审核。
