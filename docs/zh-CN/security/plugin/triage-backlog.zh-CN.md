# 历史发现分诊

> 有关完整的文档索引，请参阅 [llms.txt](https://learn.chatgpt.com/llms.txt)。通过将 `.md` 附加到页面 URL 即可获得文档页面的 Markdown 版本。

使用 `$codex-security:triage-finding` 根据当前仓库检查现有安全结果。此工作流程执行只读静态分析：Codex 将每个发现视为未经证实的声明，并检查仓库证据而不执行代码。

从范围为您要评估的仓库的 Codex 项目运行此工作流程。 Codex 必须能够读取仓库的源代码。 Jira 和 Linear 连接器可以提供查找数据，而 GitHub 查找结果需要经过身份验证的 GitHub REST 访问。两者都不能取代对源代码的访问。

在底层，Codex 从引用的代码或版本信息开始。它跟踪声称的攻击者控制的源、相关的安全控制、危险的接收器和可达路径。它还检查产品表面和信任边界，寻找矛盾证据，并记录证据差距。然后，Codex 对每个发现返回一个判决，并对需要采取行动或进一步审查的发现进行排名。

这不同于`$codex-security:validation`，它可以构建或运行代码，创建有针对性的测试或概念证明，或者使用真实的界面来重现或反驳发现。使用分类对现有待办事项进行分类和排名。当运行时证据可以解决静态证据不确定的结果时，请使用验证。

待办事项分类从现有发现开始。要在仓库中搜索新漏洞 [运行安全扫描](scans.zh-CN.md)。分类不会修改仓库或实施修复。

## 选择要分类的结果

您可以从以下来源提供一项调查结果或一组调查结果：

| 来源 | 提供什么 | 要求 |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 粘贴或本地结果 | SARIF 结果、CVE 或 GHSA、公告、扫描仪票证、错误赏金报告、Codex Security 发现工件或简单语言漏洞声明。                                                                                                                                                                                                                                                                                          | 无需连接器。                                                                                                                                                                           |
| Jira 或 Linear | 确切的安全或漏洞问题 URL 或标识符、Jira JQL 或 Linear 团队、项目或搜索短语。 Codex 在分类之前检索选定的问题内容。                                                                                                                                                                                                                                                                            | [Jira 通过 Atlassian Rovo](codex://plugins/plugin_connector_692de805e3ec8191834719067174a384) 或 [线性](codex://plugins/plugin_asdk_app_69a089a326dc8191b32a3f2553f5be2c) 具有读访问权限。 |
| GitHub | 一个仓库和一个查找源：代码扫描、`Dependabot` 漏洞和恶意软件、安全公告和私人漏洞报告或所有源。如果您不指定仓库，Codex 将使用附加到当前 Codex 项目的 GitHub 仓库（如果可用）。 GitHub 问题不包含在默认的 GitHub 源中；当您想要对 GitHub 问题进行分类时，请提供具体问题或明确询问它们。 | 经过身份验证的 GitHub REST 访问，例如 `gh auth token`、`GH_TOKEN` 或 `GITHUB_TOKEN`，有权读取所选仓库和结果类型。                                      |

Codex 按输入顺序为每个提供的发现保留一个结果，因此每个源发现都保持可追溯。它不会合并或删除看起来重复的结果。

<a id="run-read-only-triage"></a>

## 运行只读分类

对于粘贴的结果或本地工件，请发送如下提示：

```text
使用 $codex-security:triage-finding 对照此仓库对这些现有安全结果进行分类：

[Paste the findings or provide the artifact path.]
```

对于 Jira 或 Linear 问题，识别问题集并将源系统保持为只读：

```text
使用 $codex-security:triage-finding 导入和分类 [Jira 或线性问题 URL、标识符或针对此仓库的查询 ] 的安全结果。
不要改变源问题。
```

对于 GitHub 结果，命名仓库和来源：

```text
使用 $codex-security:triage-finding 导入和分类 [代码扫描、Dependabot 漏洞和恶意软件、安全公告和私有漏洞报告，或针对此仓库的 [owner/repository] 中的所有 ]。
```

要使用附加到当前 Codex 项目的 GitHub 仓库，请仅指定查找源：

```text
使用 $codex-security:triage-finding 导入和分类 [代码扫描、Dependabot 漏洞和恶意软件、安全公告和私有漏洞报告，或针对此仓库的 GitHub 中的所有]。使用附加到当前 Codex 项目的 GitHub 仓库。
```

工作流程按以下顺序进行：

<WorkflowSteps variant="headings">

1. 收集并整理调查结果

Codex 检索任何请求的问题或 GitHub 内容，保留源标识符和引用，并为每个输入创建一个分类项目。它在分配判决之前构建完整的项目列表。

2. 确认仓库上下文

Codex 解析当前仓库和修订（如果可用）。当存在时，它会读取 `SECURITY.md`，因此受支持的版本、可信输入、产品边界和超出范围的使用界面会为评估提供信息。

3. 检查静态证据

对于每个发现，Codex 都会跟踪声称的攻击者控制源、相关安全控制、易受攻击的接收器、可达路径和支持的安全边界。它记录支持证据、反对主张的证据以及证据差距。

4. 分配判决和排名

Codex 为每项发现赋予结论和信心。它根据不同队列中的可利用性对 `confirmed` 和 `needs_review` 发现结果进行排名。

</WorkflowSteps>

<a id="review-the-results"></a>

## 查看结果

| 判决结果 | | 的含义
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `confirmed` | 仓库证据表明，易受攻击的路径在规定的前提条件下是可达的，并且跨越了受支持的安全边界。                     |
| `not_actionable` | 仓库证据排除了索赔，例如通过显示未受影响的版本、无法到达的路径、有效的防护或未发货的使用界面。                 |
| `needs_review` | 仓库证据不足以做出决定，因为所需信息缺失、不明确、依赖于运行时、依赖于环境或依赖于策略。 |

可利用性排名使用从 `1` 开始的正整数，在每个判决队列中独立。这使得补救优先事项与未解决的审核工作分开。排名 `1` 是该结果集中最容易利用的 `confirmed` 结果或最高优先级的 `needs_review` 结果。该排名不是扫描仪严重性分数，并且 `not_actionable` 结果未排名。

对于每项发现，请审查：

- 判决和排名的理由
- 支持证据和反对主张的证据
- 悬而未决的问题和剩余的证据差距
- 受影响的位置和组件
- 产品使用界面和来源信任级别
- 建议的下一步
- [`$codex-security:fix-finding`](fix-findings.zh-CN.md) 切换，当结果为 `confirmed` 时

当提供的每个发现都有一个结果时，分类就完成了，Codex 保留其源标识符，并且任何不确定性都是明确的。 Jira、Linear 和其他积压记录保持不变，除非您在查看分类结果后要求 Codex 回写。

<a id="next-steps"></a>

## 后续步骤

- `confirmed`：人员接受修复结果后，使用 [`$codex-security:fix-finding`](fix-findings.zh-CN.md) 修复并验证它。分类会准备即时准备的切换，但不会自动调用该技能。
- `needs_review`：如果运行代码可以解决证明差距，请使用 `$codex-security:validation` 执行有界动态验证。通过发现声明、受影响位置、先决条件、静态证据以及分类结果的证据差距：

```text
  使用 $codex-security:validation 动态验证从待办事项分类结果中查找 [triage 项目 ID 或源 ID]。使用最现实的、有界的方法，准确记录测试的内容，并保留任何剩余的证明差距。
```

与分类不同，验证可以构建或运行代码，创建集中测试或概念证明，或者运用真实的界面。在批准建议的命令之前检查它们并保留 [Codex 审批和安全政策](../../agent-approvals-security.zh-CN.md)。

- `needs_review`：如果发现结果取决于产品策略或部署上下文，请在更改代码之前回答列出的未决问题。
- `not_actionable`：将证据保留在分诊记录中。 Codex 不会自动关闭或更新源票证。
- 查找所提供的积压工作之外的漏洞，[运行安全扫描](scans.zh-CN.md)。
