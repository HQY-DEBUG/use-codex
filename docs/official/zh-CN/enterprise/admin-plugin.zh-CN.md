# 管理员插件使用指南

> 有关完整的文档索引，请参阅 [llms.txt](https://learn.chatgpt.com/llms.txt)。通过将 `.md` 附加到页面 URL 即可获得文档页面的 Markdown 版本。

使用本指南了解管理插件如何支持常见的管理工作，准备任务，并尝试通过正确的批准和上下文提示关键用例。



[观看：ChatGPT Work 中的管理插件](https://www.youtube.com/watch?v=29SyCndnMZs)

<a id="1-understand-what-the-admin-plugin-is-for"></a>

## 1. 了解管理插件的用途

管理插件旨在帮助直接在 ChatGPT Work 内部管理设置、权限和控制。您用日常语言描述目标，插件会收集正确的输入，读取当前状态，解释它发现的内容，并指导下一个支持的步骤。

<a id="what-the-admin-plugin-is-designed-to-solve"></a>

### 管理插件旨在解决什么问题

- 将管理请求转变为清晰的工作流程，无需您编写 API 请求。
- 在做出决定或批准更改之前查看当前工作区状态。
- 显示哪些授权来源和字段支持答案，以及无法验证的任何内容。
- 在支持的更改之前暂停进行审核，然后再次读取记录以确认结果。

该插件在后台使用选定的管理 API 和批准的连接数据源。它不会结合每个管理系统、扩展您的权限或使每个 API 操作在 ChatGPT 中可用。拥有数据的系统仍然控制插件可以读取或更改的内容。

<a id="what-admin-apis-are-designed-to-solve"></a>

### 管理 API 旨在解决什么问题

管理 API 为软件提供了一种结构化的方式来请求数据或支持的操作。组织可以使用管理 API 来构建内部流程或外部工具。常见的示例包括计划报告、跨多个记录的重复工作以及与批准的系统的连接。这些工作流程通常需要工程、安全和治理审查。

您无需构建 API 工作流程即可使用本指南。本指南的其余部分以管理插件为中心。 ChatGPT 工作区管理和 OpenAI API 平台管理也保持独立，具有自己的权限和身份验证要求。

<a id="keep-credentials-private"></a>

### 将凭证保密

仅使用您组织批准的连接和秘密存储系统。切勿将真实的管理 API 密钥粘贴到 ChatGPT、Codex、文档或源文件中。

<a id="2-prepare-to-use-the-admin-plugin"></a>

## 2.准备使用Admin插件

当您想要以日常语言处理请求时，请使用管理插件来执行受支持的一次性任务。描述目标并提供稳定的 ID 或批准的报告背景。在您决定是否继续之前，该插件会显示它发现的内容或计划更改的内容。

该插件仅使用该任务授权的源、凭据和操作。它不会结合每个管理系统或为您提供更广泛的权限。原始系统仍然是真理的来源。

<a id="before-you-begin"></a>

### 开始之前

1. 找到记录所在的管理区域。
2. 收集所需的意见和批准。
3. 从只读请求开始。
4. 询问插件使用了哪些来源和字段，以及无法验证哪些内容。
5. 对于支持的更改，请在批准之前查看该计划。然后让插件再次读取记录并确认结果。

确认该插件在您的工作区中可用并且您具有所需的权限。下面的角色和访问用例反映了插件当前记录的范围。该插件可以查看角色、功能权限以及用户或组分配。确认后，它还可以将现有角色分配给现有组。

该插件无法创建角色、更改角色的权限或确认对特定连接器的访问。

分析用例需要访问连接的、经过批准的数据源。投资回报率分析还需要经过批准的业务或工程结果；仅有使用记录是不够的。

<a id="3-explore-key-admin-plugin-use-cases"></a>

## 3. 探索关键的管理插件用例

选择一个用例，将每个占位符替换为您批准的请求中的值，然后按顺序执行步骤。从只读请求开始，除非该任务是已获得批准的受支持更改。

<a id="list-workspace-roles"></a>

### 列出工作区角色

**提示尝试**

```text
列出工作区 {workspace_id} 中的角色。单独的内置角色和自定义角色。对于每个角色，解释它可以使用哪些功能并显示分配给它的用户或组。不要做出改变。
```

**步骤**

1. **收集：** 确认工作区 ID 以及您是否有权查看此信息。
2. **运行：** 请求只读角色列表。
3. **评论：** 检查角色类型、功能访问和分配。
4. **验证：** 调查任何意外情况而不进行更改。

<a id="review-one-role"></a>

### 回顾一个角色

**提示尝试**

```text
查看角色 {role_id}。用简单的语言解释其权限，显示谁拥有它，并标记任何看起来比预期更广泛的内容。不要编辑角色。
```

**步骤**

1. **收集：** 确认角色 ID 和工作区。
2. **运行：** 请求只读角色审核。
3. **评论：** 检查权限和分配是否与角色应执行的操作相匹配。
4. **验证：** 写下向角色所有者提出的任何问题。请记住，插件无法创建角色或编辑其权限。

<a id="understand-a-users-or-groups-access"></a>

### 了解用户或组的访问权限

**提示尝试**

```text
帮助我了解用户 {user_id} 或组 {group_id} 的访问权限。显示他们分配的角色，解释这些角色提供的访问权限，并指出重叠或差距。明确地说出你无法验证的内容。
```

**步骤**

1. **收集：** 使用用户或组的稳定 ID。
2. **运行：** 请插件解释一下访问方式。
3. **评论：** 检查分配了哪些角色以及它们提供哪些访问权限。注意任何重叠或间隙。
4. **验证：** 如果插件看不到某些内容，请将其标记为未知而不是猜测。

<a id="assign-an-existing-role-to-a-group"></a>

### 将现有角色分配给组

**提示尝试**

```text
在进行更改之前，请显示组 {group_id} 的当前角色并解释将添加什么角色 {role_id}。确认记录的批准人并等待我的明确批准。分配后，验证该组的更新角色。
```

**步骤**

1. **收集：** 确认组 ID 和角色 ID。检查已批准的请求和记录的批准人。
2. **运行：** 要求插件显示当前角色以及会发生什么变化。
3. **评论：** 仅当计划符合已批准的请求时才批准。
4. **验证：** 分配后，再次检查组以确认现有角色已按批准添加。

<a id="check-general-connector-permission"></a>

### 检查通用连接器权限

**提示尝试**

```text
检查用户 {user_id} 是否通过其分配的角色具有常规连接器访问权限。要求插件显示哪些权限支持其答案。如果它无法验证对特定连接器的访问，请明确说明。
```

**步骤**

1. **收集：** 确认用户 ID 和您查看用户访问权限的权限。
2. **运行：** 请求一般权限检查。
3. **评论：** 检查分配的角色以及用于回答的权限。
4. **验证：** 仅将此用作一般检查。它不证明对特定连接器或连接项目的访问。

<a id="troubleshoot-an-approved-change"></a>

### 对已批准的变更进行故障排除

**提示尝试**

```text
查看已批准的更改 {change_record_id}。将请求的结果与当前工作区进行比较。如果失败，请先检查工作区和角色。然后确认谁拥有该记录，解释问题，并建议最安全的下一步。
```

**步骤**

1. **收集：** 确认批准的变更记录和预期结果。
2. **运行：** 要求插件将请求与当前工作区进行比较。
3. **评论：** 检查工作区和角色。接下来，验证记录所有者。
4. **验证：** 在选择下一步之前，使用当前工作区状态作为事实来源。

<a id="optimize-cost-and-model-mix"></a>

### 优化成本和模型组合

**提示尝试**

```text
对于工作区 {workspace_id} 中的 {date_range}，按用例对验证的令牌使用和成本进行分组。使用可用的速度和质量信息比较模型和推理模式。当数据显示出几乎没有价值的证据时，标记成本高昂的工作流程。建议可以减少支出或将支出转向生产力或成本结果更高的工作。包括任何批准的收入或质量信号。估计可能的节省，解释权衡，并将经过验证的观察结果与假设或缺失的输入分开。保持只读。
```

**步骤**

1. **收集：** 确认工作区、日期范围以及涵盖整个期间的成本数据。检查哪些已批准的绩效或结果字段可用。
2. **运行：** 询问费用和模型比较。
3. **评论：** 将数据显示的内容与假设、缺失的输入和权衡分开。
4. **验证：** 在采取行动之前，与财务部和工作流程负责人核实可能节省的成本。

<a id="discover-usage-and-adoption"></a>

### 发现使用和采用

**提示尝试**

```text
分析 {date_range} 期间的工作区 {workspace_id}。按团队和业务职能显示任务和Token使用情况。按用例对成本进行分组。总结团队使用 ChatGPT 和 Codex 完成的任务。包括来自法律、营销和销售的示例。比较技能和插件的可用使用。仅报告工具调用、连接的应用程序和多工具工作流程（如果这些字段可用）。显示团队在哪些地方使用更高级的工作流程以及哪些地方可能有扩展空间。对最重要的{5_or_10}用例进行排名，并显示是否一小群高度活跃的用户占据了大部分使用量。不要猜测数据中没有的活动。
```

**步骤**

1. **收集：** 检查工作区、日期范围和团队映射。确保用户级别的报告得到批准。
2. **运行：** 询问使用情况和采用情况分析。
3. **评论：** 检查哪些请求的字段可用。留下遗漏的活动而不是猜测。
4. **验证：** 高使用率并不证明高级使用、商业价值或个人绩效。

<a id="measure-business-value-and-roi"></a>

### 衡量商业价值和投资回报率

**提示尝试**

```text
对于 {date_range} 的工作区 {workspace_id}，将经过验证的使用情况和成本与批准的结果结合起来。按团队和用例估算价值。包括批准的生产力、收入和质量的销售指标。比较团队和模型，以及工作流程和用户细分。根据成本对回报进行排名。显示来源和公式。清楚地说明假设、限制和缺失的输入。不要声称 ChatGPT 造成了结果。保持只读。
```

**步骤**

1. **收集：** 检查工作区和日期范围，然后确认批准的结果。查看公式和隐私规则。
2. **运行：** 要求投资回报率分析。
3. **评论：** 检查每个来源和假设。记下每个限制或缺失的输入。
4. **验证：** 仅使用不能证明投资回报率或因果关系。与财务和企业主一起审查结果。

<a id="assess-codex-roi"></a>

### 评估 Codex 投资回报率

**提示尝试**

```text
对于工作区 {workspace_id}，将 {date_range} 中经过验证的 Codex 使用情况和成本与批准的工程成果结合起来。按团队、仓库和工作流程估算投资回报率。将生产力和交付速度与代码质量和工程成本进行比较。识别显示高价值或使用许多资源的工作流程。建议对模型、推理模式或工作流程进行更改。解释权衡和不确定性。将结果呈现为可用数据中的模式，而不是证明 Codex 导致了结果。仅返回结果；不要进行更改。
```

**步骤**

1. **收集：** 确认工作区和报告期间。查看团队和仓库映射以及批准的基线数据。
2. **运行：** 请求 Codex 投资回报率分析。
3. **评论：** 区分观察到的模式和假设。保护用户和仓库数据。
4. **验证：** 与工程部门一起审查建议和结果基线。

<a id="4-when-an-api-workflow-may-make-sense"></a>

## 4. API 工作流程何时有意义

一些组织使用 API 构建自己的管理流程或外部工具。这种方法可以支持计划的或连续的工作。当流程跨越许多记录或需要连接到批准的内部系统时，它也可以提供帮助。这与引导式管理插件体验是分开的。

从定义的管理任务开始：确定所需的输入和权限、审核点、预期结果以及如何记录结果。如果您的组织将其自动化，请让适当的工程、安全和治理团队参与其中；将凭证保存在批准的秘密存储中；并在部署之前测试工作流程。
